# 출처의 수집 성공과 분석 완료를 분리

## 화면이 계속 미완료·정상 이력 없음으로 보인 이유

기존 `sources[].status`는 통신 성공뿐 아니라 사업 매칭·좌표 검증·가격 분석·전체 처리 범위를 한꺼번에 나타냈다. `last_success_at`도 status가 ok인 경우에만 기록했다. 따라서 실제 조회·저장이 성공해도 미연결 공고나 다음 날로 넘긴 작업 하나가 있으면 partial/null로 남았다. 마지막 정상 갱신 기록 없음은 실제 데이터를 한 번도 받지 못했다는 뜻이 아니었다.

11월 8일 성공 실행 42458945888도 38개 사업 중 29개 처리·9개 이월 상태였다. 경기도 공고는 처리 예산 종료, 청약홈/국토부는 분석 이월, 카카오는 일부 주소 부족이 표시됐다. 카카오의 주소 부족은 API 연결 실패와 구분해야 한다.

## 새 판정

수집 응답을 검증한 지점에서 별도 증거를 기록한다. HTTP 200이나 누적 건수만으로 성공을 판단하지 않는다.

- 정상 수집: 실제 응답의 구조가 검증됐고 이번 실행에서 관찰된 수집 오류가 없음. 0건의 정상 응답도 포함.
- 일부 응답 실패: 성공 응답과 통신/응답 검증 오류가 함께 발생.
- 수집 실패: 실제 실패 또는 잘못된 응답이며 성공 응답 근거가 없음.
- 저장 응답 사용: 캐시만 사용했으므로 실시간 연결 성공으로 표시하지 않음.
- 이번 API 조회 없음 / 미설정: 요청하지 않았거나 키가 준비되지 않은 상태를 성공으로 추정하지 않음.

`last_collected_at`은 검증된 응답의 원래 시각이다. 캐시를 읽은 현재 시각으로 갱신하지 않으며, 실패 시 이전 성공시각을 보존한다. 신규 실제 응답을 받으면 범위 미완료여도 수집 성공시각을 기록한다.

사업 매칭 실패·주소 검색 결과 없음·문서 해석 대기·분할 처리 이월은 별도의 범위/분석 안내로 표시한다. 기존 `status`, `last_success_at`, 최상위 `last_success_at`의 전체 완료 의미는 바꾸지 않는다. JSON 1.0.0에 선택 필드만 추가하여 기존 자료도 계속 유효하다.

## 기존 JSON과 적용

기존 JSON에 새 응답 증거가 없으면 현재 수집이 성공했다고 추정하지 않는다. 기존 정상 완료시각이 있으면 활용하고, 없으면 성공시각 미기록이라고 설명한다. 건수나 JSON 생성시각을 실제 수집 성공시각으로 바꾸지 않는다. 새 코드가 main에 병합되고 실제 갱신을 실행한 이후부터 새 판정 필드가 운영 자료에 기록된다.

운영 데이터·분석 기준·가격차 계산식은 직접 수정하지 않았다. 실제 API 재조회나 새 운영 실행은 하지 않았다. 테스트는 캐시 원시각 보존, HTTP 200 오류 응답, 일부 실패, 잘못된 시간대 비교, 조회하지 않은 누적 데이터, 주소 결과 없음과 수집 성공 분리, 기존 계약 호환성을 포함한다.
