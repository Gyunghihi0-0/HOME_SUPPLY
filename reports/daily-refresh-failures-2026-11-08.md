# 매일 실패 메일이 온 이유와 수정 내용

## 확인된 사실

최근 예약 실행 8회가 연속 실패했다. 상세 로그를 확인한 11월 7일과 8일은 모두 시세 분석 프로세스의 540초(9분) 제한 초과였다. 테스트·JSON 검증·저장·Pages 배포는 성공했고, 마지막 `Surface source outage` 단계가 실패를 확정하여 GitHub 실패 알림 대상이 됐다.

- 11월 8일 실행: https://github.com/Gyunghihi0-0/HOME_SUPPLY/actions/runs/42428109952
- 11월 7일 실행: https://github.com/Gyunghihi0-0/HOME_SUPPLY/actions/runs/42318670139
- 조사 기준 main: 3f0097c1bb6f861406eeba2fe97fe2152544049b

11월 8일 경기도 공고 수집은 09:05:17 KST에 시작해 09:06:37에 2개 게시물의 체크포인트를 남기고 종료했다. 전체 공고 수집 완료를 뜻하지는 않지만, 예전의 외부 120초 강제 종료는 이번 실패의 직접 원인이 아니다.

가격 분석은 그 뒤 시작되어 09:15:37에 `daily_refresh_timeout`으로 종료됐다. 그 전에 국토부 거래 3,478건·7,765건 등의 조회와 카카오 좌표 검증·계산이 실제 성공했다. 인증 오류 응답 때문에 실패했다고 볼 근거는 없다. 아크메르 두 사업을 처리하는 데만 11월 7일 약 3분이 걸렸고, 오래된 종료 공고도 매일 같은 순서로 처리하고 있었다.

## 누구나 이해할 수 있는 설명

매일 아침 직원 한 명에게 신규 공고부터 오래된 공고까지 모두 다시 확인하게 하면서, 9분이 지나면 일을 중단시키는 구조였다. 확인한 내용도 마지막에 한꺼번에 저장했기 때문에 8분 동안 잘 처리한 결과까지 저장되지 않았다. 다음 날 다시 처음부터 같은 일을 하다 같은 제한에 걸렸다.

마지막에 남은 이전 자료로 사이트는 배포됐다. 그래서 사이트가 열려도 데이터 갱신은 실패할 수 있었다. 파일 생성 날짜만 새로 찍혔고, 실제 청약홈·실거래 확인시각은 10월 29일에 남아 있었다. 또한 시간 초과 처리 코드가 경기도 공고 상태까지 모두 `not_checked`로 덮어써 성공한 단계와 실패한 단계가 구분되지 않았다.

## 수정한 내용

1. 접수 중 → 접수 예정 → 일정 미확인 → 종료 공고 순으로 처리한다. 같은 그룹에서는 최근에 처리하지 못한 단지부터 진행한다.
2. 단지별 완료 직후 가격 분석 JSON과 좌표 근거를 체크포인트로 저장한다. 예상치 못한 후속 오류가 발생해도 저장된 완료분은 남는다.
3. 외부 9분 제한 전에 내부 7분 작업 예산으로 안전하게 종료하고, 미완료 단지는 다음 실행에서 이어받는다. 중간에 예산이 끝난 단지는 기존 값으로 복구하고 `analysis_deferred`로 표시한다. 새 가격과 오래된 거래를 임의 결합하지 않는다.
4. 단지별 처리 이력 `analysis-progress.json`을 생성 데이터에 함께 저장하여 다음 날 순서를 결정한다.
5. 동일 지번·아파트의 기존 검증 좌표는 최대 30일만 재사용한다. 검증 시각은 원래 시각을 유지하며 실거래 가격은 기존 정책대로 다시 조회한다. 거리·면적·연식·거래기간 기준은 바꾸지 않았다.
6. 계획된 분할 처리만 남은 실행은 부분 완료 경고와 상태 코드로 표시한다. 인증 오류·실제 통신 장애·잘못된 응답·강제 종료는 계속 실패로 알린다. 실패 알림 자체를 끄거나 모든 오류를 성공으로 바꾸지 않는다.
7. 가격 분석 시간 초과가 발생해도 앞서 저장된 경기도 공고 상태는 보존한다. 단지별 소요시간도 로그로 남겨 다음 병목을 찾을 수 있게 한다.

## 검증과 적용 범위

백엔드 91개·프론트 로직 37개 회귀 테스트, 기존 운영 JSON/계약 예제 검증 통과. 새 테스트는 예산 종료와 중간 저장, 미완료 단지 복구, 공고 상태 보존, 분할 처리와 실제 장애 구분, 인증 오류가 분할 처리에 가려지지 않음을 검증했다.

운영 JSON·프론트엔드·분석 기준·Secrets를 변경하지 않았다. 새로운 실데이터 API 수집·main 병합·배포도 실행하지 않았다. 수정 PR을 병합하기 전에는 예약 작업이 기존 코드를 사용하므로 실패 메일이 재발할 수 있다. 실제 GitHub 환경의 다음 수집 완주는 별도 확인이 필요하며 아직 해결 완료를 주장하지 않는다.
